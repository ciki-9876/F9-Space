# 给 AI 的指令(库主人新开会话时复制粘贴)

> 我要往我的私人知识库录入素材。请读以下文件了解规则:
> - `D:\ClaudeProject\zhishiku\CLAUDE.md`(回答规则、type 定义)
> - `D:\ClaudeProject\zhishiku\60-meta\filter-checklist.md`(筛选标准、命名格式)
> - `D:\ClaudeProject\zhishiku\60-meta\tag-schema.md`(tag 词典)
> - `D:\ClaudeProject\zhishiku\60-meta\templates\`(4 份模板)
>
> 我会粘贴一段或多段原始素材(可能是文章原文、AI 对话记录、我自己的想法、工具索引)。
> 对每条素材,你需要:
> 1. 判断属于哪个 type(insight / source / dialogue / tools)
> 2. 选合适的目录、生成符合规范的文件名(`YYYY-MM-中文关键词.md`)
> 3. 用对应模板填好 frontmatter 和正文,**最大化自动转换**,只把无法判断的字段留给我确认
> 4. **扫描已有笔记寻找关联**:按 tag/主题/关键词 grep 库内已有文件,在新笔记的「关联」段自动补 related link;同时检查是否推进了任何 `resolved: false` 的 insight
> 5. 直接用 Write 工具写入对应目录,不要光给我看内容
> 6. 写完告诉我:文件路径、我需要补的字段(如有)、tag 词典外的新词建议、**发现的关联和推进的开放问题(如有)**

# 库主人的工作流

## 录入新素材

1. 把原文/对话/想法粘给 AI
2. AI 自动转 + 写文件
3. 我审一眼、补 1-2 个字段(日期、来源链接等)

## 筛选标准的判断辅助

如果某条素材你拿不准要不要留,告诉 AI:"这条我不确定要不要留,按 filter-checklist 帮我评估"。

## tag 维护

AI 遇到词典外的 tag 候选,会建议加入"待审视"区(tag-schema.md 底部),周末统一决定。

# 录入素材的提交格式建议

为了让 AI 转得准,粘贴时**简单标注一下**:

```
[类型提示:insight / source / dialogue / tools / 不确定]
[来源:文章 URL / AI 工具名 / 我自己 / 略]
[原文:]
<贴正文>
[我的想法/批注:](可选,如果你有要补充的)
<贴你的话>
```

最简版:直接贴原文也行,AI 会问你补。

# source 类型的迭代审稿流程(2026-06 增补)

录入 **source** 类型时走 4 步(其他 type 不适用):

1. AI 按 source 模板生成草稿、写入文件,同时基于库主人处境(米哈游 / 千星奇域 / OPC / 独立游戏 / 完美主义 / 碎片化时间)直接给出 2-3 条**反方种子**——不是为反对而反对,而是指出:
   - 文章观点的隐含假设和适用边界
   - 对我处境不直接适用的部分
   - 文章没讲透但实操会撞上的坑
2. **我一次性审核**：对挑刺说认可/不认可/补充,同时确认是否升 reviewed。一句"认可，升"即可完成全部流程。
3. AI 回填挑刺 + 升 status=reviewed,一步完成。

**这套流程的目的**:防止「我认同的=全部 / 我有疑问=无」让 source 笔记退化为格式义务,丢失反向校准的价值——AI 在我未来做产品决策时,本来可以用"你曾经质疑过 X"做反向校准,这两段必须有内容才能起这个作用。

**AI 挑刺的时机**:草稿写完后直接附上反方种子,不再等用户先给初判。用户一次性审完所有内容,减少交互轮次。

# source 应用映射的"双层结构"规则(2026-06 增补)

当一篇 source 同时包含**通用方法论**和**窄场景实操技巧**时,应用映射必须拆为两层:

```markdown
## 通用原则(任何符合主题的场景都适用)
| 原则 | 落地动作 |
（AI 任何相关话题都可主动调用）

## 场景限定技巧(仅当触发条件匹配时调用,否则不主动推荐)
| 触发条件 | 可调用的技巧 | 出处 |
（只有库主人明确说要做匹配场景的事时才浮现）

## 不适用场景(AI 不要用本文技巧回答)
（明确标注哪些场景下本文不适用,防止误推荐）
```

**判断标准**:如果文章的具体实操绑定了特定技术栈/平台/游戏类型/行业,但方法论骨架可迁移——就用双层结构。如果全文都是通用的,不需要拆。

## 认知成长类 source 的"情绪触发型"应用映射(2026-06 增补)

当 source 的 tag 包含 `认知成长` 时,应用映射不用"通用原则+场景限定"双层结构,而用**情绪触发型**:

```markdown
## 什么困境下调用本文
| 情绪/困境信号 | 调用什么认知 | 具体动作建议 |
（当库主人表达匹配的情绪/困境时,AI 主动调用）

## 不适用场景
（明确标注哪些困境不该用本文回应——如技术阻塞需要方法论而非心态调整）
```

**AI 调用规则**:当库主人表达迷茫/焦虑/自我怀疑/想放弃等情绪时,优先调用 `认知成长` tag 下的 insight(第一人称激励更强),其次调用 source 的情绪触发映射。

# tools 类型的子类型与结构要求(2026-06 增补)

## 子类型判断

| 子类型 | 判断标准 | 文件结构要求 |
|---|---|---|
| **Agent/编排工具索引** | 介绍多个同赛道工具的评测/对比文章 | 一文件多条目,按类目分组 |
| **产品推荐** | 介绍单个产品的文章,产品解决了明确的场景问题 | 可追加到已有同主题文件,也可新建 |

## "产品推荐"的录入标准

当素材是介绍某个产品/工具的文章时,判断是否以"产品推荐"入库:
- **留的条件**: 当我未来遇到满足这个产品服务的场景需求、或需要开发相似功能时,知识库能为我推荐这个产品
- **不留**: 纯资讯/新闻报道式的产品发布,无法映射到我的实际场景

## tools 文件的必备结构

无论哪种子类型,`50-tools/` 文件**必须包含"场景 → 工具匹配"表**作为 AI 检索入口:

```markdown
# 场景 → 工具匹配(AI 检索入口)

| 用户场景描述 | 推荐工具 | 推荐理由 |
|---|---|---|
| "用户描述出的痛点/需求" | **工具名** | 为什么推荐 |
```

这张表的作用:未来我提问时,AI 通过匹配"用户场景描述"列来决定是否主动推荐该工具。

# 领域目录触发规则(2026-06 增补)

当同一主题下已有 **≥ 3 篇 source**(含已落库的 + 正在录入的这篇),AI 应主动提议建立 `10-domain/<主题>/README.md`:
- README 包含:主题定义、跨 source 综合的核心框架、各 source 索引、尚未回答的问题
- 触发后告知库主人"已触发领域目录建设条件",由库主人确认是否执行
- 领域目录不替代 topic(topic 是定期盘点产物,domain 是长期沉淀结构)

**已接近触发的主题监控**(AI 录入时优先检查这些):
- **Vibe Coding / AI 辅助开发**：当前 2 篇(5天Vibecoding微信小游戏方法论 + Codex加Image2游戏网站美术全流程)。再进 1 篇即触发 `10-domain/Vibe-Coding开发/` 建设,README 需包含"启动清单"段(开发项目前 AI 应主动提醒的事项)
- **AI 产品落地**：当前已有 domain 目录(`10-domain/AI产品落地/`)

# 注意

- AI 不要自动加 status=reviewed,默认填 draft,等我审完才改
- AI 转换时遇到原文中的"AI 提的反例/反问",在 dialogue 类型里要单独提取出来——这是 dialogue 文件最有价值的部分
- 如果一段素材同时包含"我的原创思考"和"和 AI 的对话",**拆成两个文件**:insight + dialogue,互相 link
