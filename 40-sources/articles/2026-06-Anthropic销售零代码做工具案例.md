# 一句话摘要

Anthropic 销售 Jared Sires（零代码基础）用 Claude Code 从个人痛点出发做了邮件助手工具，4300 行代码，24 小时内自发传播，几个月后 80% 销售团队在用，他本人从 Sales 转型为 GTM Architect。

# 关键观点(3-5 条)

- **"离问题最近的人就是最该做工具的人"**：工程师想不出销售的痛，销售知道早上第一个电话前需要什么、晚上该怎么跟进、新人最缺什么。技术门槛消失后，从想法到成品不再需要中间人。
- **传播路径极简有效**：个人痛点 → 自建解决 → Slack 分享 → 24h 内同事自发采用 → 几个月覆盖 80% 团队。没有自上而下的推广，纯靠"看见效果"自发扩散。
- **工具架构 = Context + Skills + 分发**：从 CRM/日历/文档/Web 拉 context → system prompt 迭代几百遍匹配写作风格 → 封装为 20+ skills（/customer-context、/pipeline-management）→ 打包为 Cowork 插件一键安装。
- **效率增量是入口，角色转变是终局**：表面省 10-15 小时/周，真正价值是"从行政工作回到销售本身"——从执行者变为策略制定者。职业路径：Sales → GTM PM → GTM Architect。
- **新人 onboarding 从数周缩短到第一天**：插件即工作流，20+ skills 直接可用，接好了 Salesforce/Intercom/Gong/Calendar/Gmail/Drive/BigQuery。

# 我认同的

- 全部认同，尤其"离问题最近的人做工具"——我就是那个人
- 传播路径（痛点→自建→分享→自发采用）可复制
- API 调用成本不是障碍（米哈游也有几乎无限的 API 调用额度）
- 同事也是天然 AI 拥趸（米哈游内部大力鼓励 AI）
- 条件比 Anthropic 差异没文章暗示的那么大——合规约束具体情况具体分析，不涉及合规的场景完全可以快起来

# 我有疑问 / 不认同的

> 以下由 AI 挑刺，我审核认可：

- **单点故障风险**：4300 行代码全团队依赖一个人的 side project = Key Person Risk。如果做工具的人离职/转岗/生病，工具谁维护？从"个人工具"推向"团队工具"时，必须有交接性设计（prompt 文档化、skill 可被他人迭代、不依赖单人隐性知识）。推广阶段的产品化程度要求比文章展示的更高。
- **合规场景节奏不同**：涉及玩家数据/内容安全的场景需过安全审查，传播速度会慢于不涉合规的内部工具场景。方向对，但不是所有场景都能 24h 跑通。

# 应用映射(给未来 AI 看的应用指引,不是读后感)

> 当我在做相关工作/产品落地时,AI 应直接调用此段,而不是泛泛摘录全文观点。

## 通用原则(任何符合主题的工作场景都适用)

| 原则 | 落地动作 |
|---|---|
| 离痛点最近的人做工具 | 不要等工程团队排期，运营自己最懂痛点——用 Claude Code 先做出能跑的 demo，再找工程师 polish |
| 传播靠"被看见"不靠推广 | 做出工具后在团队群/Slack 分享，让第一个外部用户自然出现；一旦有人用，效果自传播 |
| System prompt 是核心资产 | 迭代几百遍才调通——prompt 的精细度决定工具可用度，不是写完一版就能用 |
| 插件化 = 规模化 | 个人工具验证后，打包为可一键安装的 skill 集合（而非要求每个人自己配置），降低采用门槛到零 |

## 按场景的具体落法

| 工作场景 | 关键应用点 |
|---|---|
| 千星奇域运营日常（类似 Sires 的"邮件深渊"） | 找到运营每天最耗时的重复动作（审核回复？数据拉取？周报？），用 Claude Code 做一个"每日简报"式 Agent，先自己用 → 再给团队用 |
| Agent 业务闭环的推广策略 | 不要搞全员培训/强推。参考 CLAFTS 路径：一个人做出来 → 群里分享 → 有人自发试 → 效果说话 → 自然扩散。产品设计要支持这个路径（易分享、一键装、开箱即用） |
| 新人 onboarding | 把团队积累的 skill 打包为"新人 starter kit"——入职第一天装上，20+ 业务 skill 直接可用，无需数周摸索 |
| 运营人员的角色升级路径 | 本案例证明：运营做工具 → 理解产品逻辑 → 成为产品设计者。后台产品可以为这个成长路径留出空间（允许运营自建 skill、提供 skill marketplace） |
