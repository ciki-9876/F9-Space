# 问题(尚无完整结论)

当一个非工程师用 AI 做出工具、推广到团队依赖后——如果这个人离职/转岗/生病，工具谁维护？

本质是：**超级个体的 side project 变成团队基础设施后，Key Person Risk 如何系统性消解？**

# 目前能拼出的方向（来自库内 source）

| 方向 | 来源 | 成熟度 |
|---|---|---|
| **Skill 化**：把隐性知识封装为可执行的 skill 文件，别人拿到就能跑 | 超级个体报告 | 方向明确，缺实操模板 |
| **透明化**：prompt、context 配置、迭代逻辑写成文档，放共享位置 | 超级个体报告（CodeBuddy monorepo） | 方向明确，缺"prompt 文档化"最佳实践 |
| **模块化**：工具拆成独立 skill，每个有明确输入输出，可独立理解和修改 | 腾讯AI下半场（Skills > Features） | 方向明确 |
| **插件化分发**：从本地脚本升级为可安装插件 | Anthropic 案例（Cowork 插件） | 有案例但无通用做法 |
| **找第二维护者**：至少一人能理解并修改 | 常识推断 | 缺方法论（交接成本怎么控制？） |

# 尚未回答的子问题

- "prompt 文档化"具体该记录什么？（设计意图？迭代历史？失败尝试？）
- 非工程师做的工具如何进入公司正式工具链（从 side project → IT 支持的正式工具）？
- "第二个维护者"怎么低成本培养？交接文档 vs pair session vs 直接让 AI 解释代码？
- 是不是应该从一开始就以"可交接"为设计约束，而非做完再补文档？

# 对业务的启发

- 我在做千星奇域运营工具时，从第一天就要考虑"如果我不在了这东西还能跑吗"
- 产品设计层面：后台应内置"skill 可被他人 fork/迭代"的机制，而非只支持个人使用
- 这可能是"个人工具 → 团队产品"的必经之路，也是我作为产品运营能贡献的产品设计洞察
