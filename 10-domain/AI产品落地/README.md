# AI 产品落地：跨篇方法论沉淀

> 本目录是从 3 篇 source 中抽取的**可复用方法论框架**，专门服务于千星奇域产品运营后台 + Agent 业务闭环场景。
> 每条原则后面标注了来源，便于溯源。

---

## 核心公式

**组织竞争力 = 人才密度 × AI杠杆 / 组织摩擦**

- 提升杠杆：给完整问题、给工具权限、给展示舞台
- 降低摩擦：减审批、异步沟通、缩短从想法到交付的链路
- 保护密度：不让不适配的人稀释团队

## AI 产品落地的 5 层设计栈（由底向上）

| 层 | 是什么 | 关键原则 | 来源 |
|---|---|---|---|
| **L1 基座** | 通用大模型 | 用通用基座，不为单产品训垂类；性能 > 架构，robustness on 长尾 | 腾讯AI下半场 |
| **L2 Context** | 结构化场景信息 | Context 是 Agent 的氧气——什么是好/坏、约束、数据、状态；PRD 核心从 UI 转向 context schema 设计 | 腾讯AI下半场 |
| **L3 Skills** | 可调用的原子能力 | 功能拆成 Agent 可调用的 skill（清晰输入输出、独立测试、可复用）；经验传递靠递 Skill 不靠说话 | 腾讯AI下半场 + 超级个体报告 |
| **L4 编排** | Agent 工作流 / 多 Agent 协调 | MetaSkill 声明式编排（给目标 + skill 库，Agent 自动组装）；AI 协调三阶：透明化 → 路由替代中层 → 主动编排 | Agent工具篇 + 超级个体报告 |
| **L5 人机界面** | UI / 人工兜底 | 模型越强产品越简化；UI 是 Agent 不确定时的人工兜底入口，不是主入口；每次模型升级应能让 UI 减一层 | 腾讯AI下半场 |

---

## 落地节奏：先做什么

```
1. Context 设计（L2）→ 决定 Agent 能力上限
2. Skills 拆解（L3）→ 决定 Agent 可做什么
3. 最薄 UI 兜底（L5）→ Agent 做不了的人来补
4. 数据回流闭环 → 模型随产品进化
5. 编排升级（L4）→ 从单 Agent 到多 Agent 协调
```

**反过来做（先设计 UI → 再想 Agent 放哪）是最常见的失败模式。**

## 千星奇域场景对照表

| 业务场景 | 适用团队形态 | 设计重心 | 边界条件 |
|---|---|---|---|
| **UGC 内容审核** | AI 中枢型（Agent 主动编排，人做边界判断） | L2 Context：什么是违规的结构化规则 + L3 Skill：分级审核能力 | 安全门控不可去掉，只能让人聚焦边界 case |
| **关卡孵化/创作者工具** | 网络协作型（无中心，多角色各自闭环） | L3 Skills：创作辅助原子能力 + L5 UI：创作者友好的交互 | 创意场景需要人的品味判断，Agent 做执行不做方向 |
| **运营后台 Agent 闭环** | 节点辐射型 → 逐步向 AI 中枢型演进 | L2+L4：运营 context 结构化 + 任务编排 | 先做信息透明（L4 第一阶），再做路由替代 |
| **数据分析/指标看板** | AI 中枢型 | L3 Skill：数据查询/可视化能力 | 运营可自己通过 Agent 建看板，不等 IT 排期 |

## 3 条跨篇一致的核心判断

### 1. "叠加 AI" vs "围绕 AI 重新设计" 是 2x 和 10x 的分水岭

- 把 AI 加到现有流程上 → 20-40% 效率提升
- 围绕 Agent 重新设计流程 → 2-10x 潜力

**对我意味着**：千星奇域后台不是"给现有运营工具加个 AI 按钮"，是从 Agent 视角重新设计整个运营链路。

### 2. Context > Model > UI

三篇一致指向同一个优先级：喂给 Agent 什么信息（context）比用什么模型重要，比做什么界面更重要。

**对我意味着**：产品 PRD 的核心工作量应该花在 context schema 设计上——把"什么是好内容""什么该干预""运营历史决策"结构化。

### 3. 组织变革是产品设计的一部分

AI 产品不只改变用户体验，它改变组织运作方式。产品设计必须考虑：谁用、怎么用、用了之后角色关系怎么变。

**对我意味着**：做后台产品时要同时想清楚——Agent 接管后，运营的角色从"执行者"变成"判断者+监督者"，产品要为这个角色迁移提供支撑（透明化 Agent 决策过程、提供快速干预入口）。
