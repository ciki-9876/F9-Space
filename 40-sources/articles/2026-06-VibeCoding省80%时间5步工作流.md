# 一句话摘要

Vibe Coding 日常执行的5步工作流：写规矩手册（CLAUDE.md）→ 先写测试再让AI实现（TDD）→ 每次只给一个文件（精确上下文）→ 最简技术栈（AI准确率更高）→ 每次改动就commit（存档点）。核心节奏：一天 coding 不超过2小时，剩余时间"想清楚该做什么"。

# 关键观点

- **CLAUDE.md = AI的handbook**：项目规矩只写一次，包含构建命令/代码风格/禁止事项/项目背景。"每天早上要重新跟实习生讲一遍规矩，还是让他入职第一天就看handbook？"
- **TDD思路（最大认知升级）**：先定义期望的输入输出（测试）→ 再让AI写代码通过测试。好处：AI有明确交付标准/测试是你的预期不是AI自编/改代码时测试兜底。"让学生自己出题自己考，永远100分"——所以要你出题AI考。
- **每次只给一个文件**：越具体越不出错+省token。"叫外卖：'随便帮我点个午饭' vs '麦当劳巨无霸套餐去冰'——哪个出错概率高？"
- **最简技术栈**：简单代码在AI训练数据中出现百万次，复杂架构样本少。Express > NestJS+GraphQL+Prisma。"stdlib能做的不加第三方包"
- **每次改动就commit**：不需要漂亮的commit message，"AI改了Header组件"就行。一天commit二三十次。"打游戏不存档，死了从头来。"
- **时间分配翻转**：以前80%写代码+20%想需求，现在反过来。"AI越强，'想清楚要什么'的时间比例越高。"

# 我认同的

- 作为未来 Vibe Coding 的日常执行参考。TDD思路（先定义"什么算完成"再让AI实现）对我尤其有用——对冲我的完美主义（先写测试=先定义60分标准，AI通过就算完成）。

# 我有疑问 / 不认同的

- **"每次只给一个文件"在 Titan 平台可能不完全适用**：Titan 的 AI（当前即我）有1M context可以同时读很多文件。"只给一个文件"是 Claude Code CLI 的 token 节省策略，在大 context 模型上精确指令比限制文件数更重要。→ **调用规则**：核心原则是"精确"而非"少"——告诉AI改哪里、改成什么，比控制给多少文件更关键。

# 应用映射(给未来 AI 看的应用指引)

> **调用时机**：当福九开始 Vibe Coding 开发项目时，作为日常执行工作流参考。

## 通用原则

| 原则 | 落地动作 |
|---|---|
| 规矩写一次省百次 | 项目开始就写好 CLAUDE.md/规则文档，包含风格/禁止/背景 |
| 先测试后实现（TDD） | 每个新功能先花5分钟写3-5个测试case，然后说"让这些测试通过" |
| 精确 > 模糊 | 说清楚"改哪个文件的哪个部分改成什么"，不说"帮我看看整个项目" |
| 简单技术栈 | 一个框架能搞定不用两个，stdlib能做不加包 |
| 频繁commit | 每次AI改完一个小单元就commit=存档点。改崩了秒回滚 |
| 2小时coding + 其余时间想需求 | 高强度coding控制在2小时内，剩余时间做"想清楚做什么"的高价值工作 |
