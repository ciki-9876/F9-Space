# 一句话摘要

某自媒体作者(已自造过"女娲""达尔文"两个 skill 工具)评测开源 agent 项目 OpenSquilla 3.0 时,提出 agent 技能管理的"三块拼图"——**造、优化、组织**,把 OpenSquilla 的 MetaSkill 视为"组织"层方案;并延伸出"卷 Harness 不卷模型"的产品哲学:agent 产品的真正差异化不在模型本身,而在模型外的那层壳(智能路由、技能编排、token 经济、上下文工程)。

> ⚠️ **来源可信度提示**:OpenSquilla / OpenClaw / Hermes Agent 这几个项目我无法在不联网时核实真实性。文章读感偏评测推荐,具体产品声明(star 数、基准对比、自动认领 134 技能等)引用前建议自行核实。但**核心思想独立于具体项目**,这是本篇的真正价值。

# 关键观点

1. **Skill 管理的三块拼图**:
   - **造**:用 AI 把人的工作流抽象成 skill(作者的"女娲")
   - **优化**:让 skill 自动版本迭代、低分版本进化为高分(作者的"达尔文")
   - **组织**:把多个 skill 编排成可执行流水线(MetaSkill 补的这块)
   前两块是单点能力,第三块是元能力。作者认为当 skill 数量爆炸,组织层是 agent 系统的真正瓶颈。

2. **MetaSkill 是 declarative 编排**:不是预先画死流程图让 agent 照跑,而是给 agent 目标 + 可用 skill 库 + 安全规则,**让 agent 自己现编流程**。区别在于:"我画好路线图你照走"→"我给你地图和规则,你自己找路"。

3. **卷 Harness 不卷模型**:Harness 是模型外的壳(变速箱、油门、导航——智能路由、skill 管理、token 优化、上下文工程)。当基座模型差异在收敛、价格在内卷,Harness 才是产品力的真正差异点。

4. **智能路由的产品意义不只是省钱**:把"选模型"从用户手里拿走。作者观点:让用户在下拉菜单挑模型,本身就是"产品没做好分内的事";自动路由是产品成熟度的标志。文章举证 25 任务基准:路由方案 vs 单用 Opus 分数几乎一样,成本差一个数量级。

5. **个人 skill 资产的兼容性是平台门槛**:OpenSquilla 开机自动认领用户 Claude Code 里的 134 个技能。作者认为这是平台必须做的事——技能生态在爆炸,但用户真正用的是自己攒的那一小撮,不让用户从零重配是平台的及格线。

6. **白盒约束 vs 黑盒自由**:MetaSkill 让 agent 自由编排,但 runtime 强制校验依赖顺序、工具白名单、风险等级、模板安全。"既让它自己组织,又上护栏"——这是 declarative 编排在生产环境跑通的关键。

# 应用映射(给未来 AI 看的应用指引,不是读后感)

## 通用原则(任何 AI 产品落地都适用)

| 原则 | 落地动作 |
|---|---|
| **三块拼图诊断** | agent 系统瓶颈分三层:skill 不够 / skill 不准 / skill 不会编排。项目启动期先判断**当前真正瓶颈在哪一层**,不要错配资源——很多团队卡在第三层却还在猛造第一层 |
| **Declarative 优于 Imperative 编排** | 不让用户/产品经理预先画工作流,而是设计"目标输入 + skill 注册表 + 规则约束"三件套,让 agent 自己组装。PRD 重点从"画流程"变成"列 skill + 写规则" |
| **Harness 是真正的产品力** | 当所有团队都用相似基座模型时,差异化机会在 Harness 层:路由、skill 编排、token 经济、上下文工程、错误恢复。投入排序:Harness > 模型 > UI |
| **自动路由 = 隐藏复杂度** | 多模型选择不应暴露给用户。系统内部按任务难度自动分配,用户感知"一个 AI"——这是产品成熟的标志,不是工程偷懒 |
| **个人 skill 资产兼容性** | 做 agent 平台必须支持"带 skill 入场"——能扫描/兼容用户已有的 Claude Code skill / Coze 工作流等。从零重配是平台死亡信号 |
| **白盒护栏(自由编排 + 强约束)** | 让 agent 自由编排时,必须强制声明:依赖顺序、工具白名单、风险等级、文件读写权限。Runtime 拒绝执行不合规的编排——既要灵活,又要可审计 |

## 按 AI 产品形态的具体落法

| 场景 | 关键应用点 |
|---|---|
| **千星奇域运营后台 + Agent**(关卡孵化、UGC 治理、内容审核) | 三块拼图诊断结果:第一块"造"(运营动作 → skill 抽取)+ 第三块"组织"(运营给目标"孵化某类关卡",agent 自己拼链路)是 1.0 核心;第二块"优化"等数据攒够再做。**不要一上来就让运营画工作流**,直接做 declarative 入口——运营给目标和约束,agent 自己组装 |
| **AI 平台/中台类产品** | 必做三件套:1) 多模型智能路由(隐藏选择复杂度);2) skill 注册表(支持业务方挂自定义 skill);3) 编排约束 runtime(防止 agent 失控)。这是平台型 AI 产品的标配,缺一就不是平台 |
| **嵌入式 AI 功能**(如文档/IDE 内 AI) | 重点**不是** MetaSkill——嵌入场景里 skill 数量少而精,自由编排反而是负担。这种场景应该走 imperative 路径,把 skill 库精挑细打磨 |
| **C 端 AI 助手**(类似元宝) | 智能路由的产品价值远大于"省钱"。把模型选择隐藏掉是必须的——下拉菜单选模型是反产品力 |
| **任意 agent 系统启动期** | 决策顺序:1) 当前瓶颈在三块拼图哪一块? 2) 如果在"组织"层,先做最小可用的 declarative 编排(三五个 skill 串起来)+ 强护栏,**不要一上来追求 OpenSquilla 那种全自动**——会被复杂度淹死 |

# 术语对照(英文概念 ↔ 中文)
