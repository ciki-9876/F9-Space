# 一句话摘要

一个程序员用 Claude Code 5 天（117 条对话、14 个 JS 文件）做出完整微信小游戏「碰个瓶」（倒水排序），全文拆解为可复制的 9 课方法论：spec 先行、prompt 分级、多模型协作、数据驱动修 bug、零引擎架构、人机分工。

# 关键观点(5 条)

- **花 30% 时间写 spec，省 70% 返工**：spec.md 是"单一事实来源"，包含技术边界、游戏规则、视觉参数（精确到 px/rgba/ms/缓动函数）、数据结构、资源分工表、验收标准。每次改逻辑必须同步更新 spec。
- **Prompt 效率差 10 倍——4 级写法**：Level 1"做好看点"（迭代 5+ 轮）→ Level 2"左亮右暗"（2-3 轮）→ Level 3 精确参数（一次过）→ Level 4 渲染顺序+全参数（一步到位）。视觉类 prompt 必须数字化，不能用形容词。
- **多模型协作 = 效率最大化**：你用眼睛判断好坏 → 视觉大模型"翻译"差异为精确技术参数 → Claude Code 按参数写代码。三个角色各做最擅长的事形成闭环。
- **人机分工清晰**：AI 一次搞定纯逻辑（倒水引擎/Undo/关卡生成/Tween/API 封装），人必须迭代视觉（瓶子外观 15+ 轮、动画节奏、配色微调、产品取舍）。AI 是执行力，人是判断力。
- **零引擎架构可复用**：微信 Canvas 2D + 14 个文件的固定架构（base/data/objects/scenes/utils），每个新游戏只改游戏逻辑部分，基础设施一条 prompt 生成。

# 我认同的

- 方法论骨架可迁移：spec 先行、prompt 分级、多模型协作、数据驱动 debug、人机分工——这些与游戏类型/引擎无关
- "你是产品经理 + 美术总监 + QA，AI 是工程师 + 动画师"的 OPC 分工模型
- 也可能用到 2D 休闲游戏的具体技巧（微信小游戏是一种可能的产品形态）

# 我有疑问 / 不认同的

> 以下由 AI 挑刺，我审核认可：

- **作者水平有限，作品效果一般**：作者是程序员做休闲小游戏（倒水排序），不是顶级独立游戏开发者。具体技巧（Canvas 2D 渲染参数、零引擎架构）绑定了最简单的游戏类型，不能直接套到 3D/中重度游戏。
- **适用边界窄于文章暗示的**：文章标题说"你也可以做到"，但"5 天做一款游戏"的预期仅适用于 2D 休闲小游戏。不同游戏类型（3D/叙事/中重度）、不同引擎（Unity/Unreal/Godot）、不同美术管线（3D 建模/骨骼动画/材质），在大方向相似但细节差异巨大。
- **"5 天"节奏给错误预期**：对简单 2D 解谜成立，对有深度的独立游戏可能是 5 个月。方法论可参考，周期不可参考。

# 对我有用的部分

> "Vibecoding 的本质不是'让 AI 写代码'——而是把你变成一个有 AI 助手的全栈团队。你是产品经理（写 spec）+ 美术总监（审视觉）+ QA（报 bug）。AI 是前端工程师 + 动画师 + 平台适配专家。"

> "花 30% 时间写 spec，节省 70% 的返工时间。"

> "描述差异点是你要做的事。你不需要知道怎么修，但你需要指出哪里不对。"

> "你不需要会写 Canvas 渲染代码，但你需要会说'左侧高光条 8px 白色 opacity 0.25'。"

> 规律：静态不变的东西 → AI 生图；需要交互/动画的东西 → Canvas 代码绘制。

## 通用原则(任何 AI 辅助开发/游戏开发场景都适用)

| 原则 | 落地动作 |
|---|---|
| Spec 先行 | 动手前写规格文档,包含技术边界+规则+验收标准;每次改逻辑同步更新,保持"单一事实来源" |
| Prompt 精确度决定效率 | 越具体越省迭代——形容词(5+轮) → 方向(2-3轮) → 精确参数(一次过)。视觉类必须数字化 |
| 多模型协作闭环 | 人判断好坏 → 视觉模型"翻译"为技术参数 → 编码模型实现。各做擅长的事 |
| 数据驱动修 bug | 先加 log/debug 输出 → 拿真实数据 → 带根因分析给 AI。不说"这里不对"让 AI 猜 |
| 人做判断,AI 做执行 | 逻辑/规则/封装交 AI;视觉/节奏/品味/产品取舍由人迭代——AI 是手,人是眼和脑 |
| 静态生成,动态代码 | 不需要交互的素材用 AI 生成;需要动画/物理/交互的用代码实现 |
| 一个人 = PM + 美术总监 + QA | OPC 分工模型:你定方向、审效果、报 bug;AI 写代码、做动画、适配平台 |

## 场景限定技巧(仅当触发条件匹配时调用,否则不主动推荐)

| 触发条件 | 可调用的技巧 | 出处 |
|---|---|---|
| 做 2D 休闲小游戏 / 微信小游戏 | 零引擎 14 文件架构(game.js + base/data/objects/scenes/utils);Canvas 2D 原生 API;4MB 包体控制策略 | 第五课 |
| 用 Canvas 2D 做视觉效果 | spec 视觉参数模板(px/rgba/ms/缓动函数);渲染层级顺序描述法;2.5D 玻璃质感实现路径 | 第一课模块3 + 第三课 |
| 微信平台相关开发 | wx.* API 封装模式;wx.createInnerAudioContext 音频;wx.createRewardedVideoAd 广告;wx.setStorageSync 存档 | 第五课 |
| 用 AI 迭代 2D 动画效果 | "三段式"prompt（角色 + 数字化参数 + 交付格式）;"翻译"模板([贴截图A+B] + 差异点 + "请输出 Canvas 2D 技术参数") | 第二课 + 第三课 |
| 遇到视觉 bug 反复出现 | 3 套 bug 报告模板：视觉对比型(ASCII图) / 数据驱动型(log→数据→根因) / 优先级标签型(P0/P1/P2+验收清单) | 第四课 |
| spec 文档需要模板参考 | 6 模块 spec.md：技术边界(必写) + 游戏规则(必写) + 视觉参数(必写) + 数据结构 + 资源分工表 + 验收标准 | 第一课 |

## 不适用场景(AI 不要用本文技巧回答)

- 3D 游戏开发 → 引擎/美术管线/参数体系完全不同,仅通用原则可参考
- 中重度/叙事型游戏 → 周期预期(5天)和架构复杂度不可类比
- 非游戏类开发 → 仅"spec 先行""prompt 分级""数据驱动 debug"三条通用原则可迁移
