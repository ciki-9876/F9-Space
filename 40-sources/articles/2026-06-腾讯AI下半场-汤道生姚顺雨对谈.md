# 一句话摘要

姚顺雨(ReAct 提出者、腾讯首席 AI 科学家)与汤道生在 2026 腾讯云 AI 产业应用大会上首次公开对谈,系统阐述了腾讯 AI 的核心打法——co-design(模型与产品深度耦合)、context 是 Agent 的氧气、长期主义——并回应"腾讯 AI 慢了吗":AI 是马拉松,下半场刚开始,未来会更多元而非单一。

# 关键观点(6 维)

1. **AI 下半场的定义**:上半场是"找好方法"(为每个任务做专门模型),下半场是"找好问题"——大模型像通用锤子,真正稀缺的是把它用在哪、能不能跑通闭环;在这个语境下,腾讯的优势是好场景 + 好 context。

2. **Co-design 三原则**:
   - 基座 solid(预训练做得 product-agnostic 但极强)
   - 后训练量体裁衣(实用价值 > benchmark 排名)
   - 数据回流闭环(产品输出回流到训练,持续迭代)

3. **能力的复合性**:LLM 时代不是单点优化,一个 Coding Agent 同时需要 reasoning / planning / 长上下文 / 工具调用。**多产品场景的数据互为反哺**,形成网络效应——做产品矩阵比单点深耕更利于模型。

4. **性价比的真相**:性能 > 架构。性能差的"便宜模型"反而费钱(任务做不对、人力补)。中国市场更需要的是**小模型 + 长尾任务的 robustness**,而非 SOTA 突破。测试集应来自真实产品而非通用 benchmark。

5. **Agent 时代的产品哲学**:模型越强,产品越简化。产品经理的工作从"设计每个功能"转向"为模型提供 context 和 skills"。不同 Agent 的差异不在交互形态,而在该场景下的 context 是否结构化。

6. **组织形态**:小团队敏捷探索 + 大平台 AI Infra(Furnace、评测、对齐)支撑——双层结构。这是大厂在 AI 时代的优势:多个小团队在同一基础设施上并行试错。

# 我有疑问 / 不认同的

> 以下 3 条由 AI 基于我的处境(米哈游 / 千星奇域 / 运营后台)反向挑刺,我审核后认可,作为应用这篇方法论时的边界条件。

1. **"模型越强 → 产品越简化"在 B 端运营后台未必成立**
   文章的隐含场景是 C 端(元宝/对话产品)。运营后台有 C 端没有的硬性需求:审计回溯、多角色协作、回滚干预,这些是流程复杂度,不是 Agent 智能能消除的。
   **校准**:这条原则在 C 端 AI 助手成立,在 high-stakes 后台要反向理解——简化的方向不是"UI 砍少",而是**让 Agent 决策的中间过程透明化**,让运营能快速判断哪里靠谱、哪里要插手。

2. **Co-design 的"数据回流"在运营场景极易被污染**
   文章把数据回流讲得像水到渠成,但运营动作回流到训练信号有几个实操坑:动机污染(KPI 压力 / 关系户 / 活动需要)、运营间标注不一致、稀疏性(下架等高干预动作低频)、反馈延迟(关卡是否优质要看长期留存而非当天动作)。
   **校准**:做 co-design 时,**数据回流的 schema 设计(每个动作的动机标签、置信度) + 标注治理(谁有权打标、冲突怎么解)的优先级高于"建回流通路"本身**。文章没讲这层,容易让人以为打通通路就完事。

3. **"产品矩阵反哺模型"是腾讯立场的辩护,不直接适用于米哈游**
   姚顺雨讲"产品矩阵 → 网络效应 → 模型反哺"是腾讯优势叙事,他们矩阵(微信/QQ/文档/元宝/Coding Agent)数据高度互通。米哈游的矩阵性质完全不同:各游戏(原神/崩铁/绝区零/千星奇域)玩家行为差异极大,运营 context 几乎不通用,HoYoLAB 又是另一个池。
   **校准**:对千星奇域,**单产品深耕的 co-design 比追求"AI 中台跨游戏复用"更现实**。如果被这条原则说服去推统一 AI 中台,实际收益可能远低于预期——游戏行业的"产品矩阵"和互联网平台的"产品矩阵"不是一种东西。

# 对我有用的部分

> "随着模型能力加强,我们把产品做得更简化了,更多的是给模型提供更多的 context,创造更多的 skills,让模型能够更高效地去完成任务。"——汤道生

> "实用的价值是大于很多 benchmark 排名的价值。Co-design 很关键的一点就是要产生闭环。"——姚顺雨

> "如果我们做一个相对较小的模型,但是它比肩大模型性能,而且在大部分任务上做很强的 robustness,这可能在很多长尾任务上面提升一两个点,可能在今天的中国更有价值。"——姚顺雨

## 通用原则(任何 AI 产品落地都适用)

| 原则 | 落地动作 |
|---|---|
| **Co-design 三角**(基座 solid → 后训练量体裁衣 → 数据回流闭环) | 1) 优先用通用基座(如混元),不为单产品训垂类模型;2) 后训练只对齐**该产品独有的判断**(如"什么是优质内容");3) 用户/运营动作必须设计回流路径,否则模型不会随产品进化 |
| **Context 是 Agent 的氧气** | PRD 的核心从 UI 设计转向**结构化场景信息**——什么是好/坏、有哪些约束、用什么数据判断、上下文有哪些状态;这些是给 Agent 的输入,产品做不好 context,模型再强也无效 |
| **Skills > Features** | 把功能拆成 Agent 可调用的 skills(原子能力 + 清晰输入输出),而不是面向人的菜单按钮;每个 skill 应能独立测试和复用 |
| **模型越强,产品越简化** | 不要先建复杂 UI;先做 skills + context 层,UI 是 Agent 不确定时的人工兜底入口,不是主入口;每次模型升级应能让 UI 减一层,而不是加一层 |
| **性能 > 架构创新,robustness on 长尾** | 不追 SOTA、不追新架构;追"99% 长尾场景能稳定做对";长尾 robustness 通常比头部任务突破更直接转化为商业价值 |
| **测试集来自真实产品** | 不用通用 benchmark 验收上线;从历史真实数据(已通过/已下架/已干预案例)构建私有评测集;**产品场景的 benchmark 是核心资产** |
| **能力复合性,产品矩阵反哺模型** | 单产品垂直优化收益有限;同一基座在多场景训练会产生网络效应——一个产品的数据能提升其他产品的模型表现,这是布产品矩阵的隐性回报 |

## 按 AI 产品形态的具体落法

| 产品形态 | 关键应用点 |
|---|---|
| **运营/管理后台 + Agent 业务闭环**(如千星奇域关卡孵化、内容审核、UGC 治理) | Context 设计是命门:把"什么是优质内容"结构化(玩法新颖度、留存数据、UGC 信号、过审历史)喂给 Agent;运营的标记/推荐/下架等动作必须有回流通路;UI 退化为 Agent 不确定时的人工兜底入口,而不是 dashboard 堆砌 |
| **C 端 AI 助手 / 对话产品**(类似元宝) | Co-design 闭环要打通:多轮交互、推理过程、用户反馈数据回流到模型;不要为助手单训垂类模型;**别迷信 benchmark**——产品里高频使用的能力跟 benchmark 经常脱节 |
| **嵌入现有产品的 AI 功能**(如文档/协作里的 AI、IDE 里的 Coding Agent) | 重点不是功能多,而是**该场景下私有 context 的注入质量**(代码库、协作历史、领域术语);robustness 在该场景的特定任务上达到可信赖,比覆盖更多任务更重要 |
| **生产力 Agent**(Coding Agent、Research Agent) | 需要复合能力(reasoning + planning + 长上下文 + 工具调用),单一能力优化没用;**评估必须基于真实任务**而非 SWE-bench 等公开测试集——后者已严重失真 |
| **任意 AI 产品启动期** | 决策顺序:先想清楚 context 来源 → 再设计 skills → 再做最薄 UI;不要倒过来从 UI 出发设计 |
